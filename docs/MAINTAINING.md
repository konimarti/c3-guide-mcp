# Maintaining c3-guide-mcp

For people who change or release the server. Users: see the [README](../README.md).

## How it works

- Layers (a module imports only the ones before it): leaves `util`, `corpus`, `context`, `ts`, `sources` (the files and libraries a project.json stands for); the process layer `proc` (run a program with a deadline and capped output, scratch directories) then `compiler` (find c3c, its version and standard library, the notes that say when the docs and the compiler differ); `guard` (refuse sources that read outside their project at compile time) and `format` (c3f); `search` and `outline` (the project and its declarations, references and rename plans, read with tree-sitter); `hints`; `check` (`c3_check`, `c3_test`, `c3_run`); `live` (the standard library as the installed c3c has it); `tools` (`c3_lookup`, `c3_refs`, `c3_search`); `setup` (`--setup`, `--doctor`); `main`.

- The docs are a snapshot embedded in the binary (`$embed` of `data/corpus.dat`, 1.8 MB), built by `scripts/gen_corpus.py` from a `c3c` install: `MANUAL.md`, `releasenotes.md`, `c3c --list-*` and `c3c docgen lib/std --json`, plus the example programs in `recipes/`. It belongs to one c3c version, printed in its header.
- A search scans every entry (BM25 over words, title hits weighted higher, recipes boosted) in a few milliseconds, so there is no index to build or keep in sync. Symbol lookups also use `data/synonyms.txt`.
- `src/context.c3` keeps the standard library modules the session works with (imports of code given to `c3_check`, of a file given to `c3_check`, `c3_lookup`, `c3_test`, `c3_run` or the `file` parameter of `c3_search`, and the module of each name `c3_lookup` found), and the project the session works on: the last project directory given to any tool, which `c3_lookup` and `c3_refs` search when no `path` is given: the newest 16, in memory only. Symbol search multiplies the score of a name from one of them by 1.5, and `c3_search` counts such a name as one more matched word when it decides whether to show the library first. Tests call `context::clear()` before any ranking check.
- When the installed c3c is not the snapshot's release, `src/live.c3` replaces the snapshot's standard library symbols with ones read from that compiler (`c3c --trust=none docgen <lib/std> --json`). It runs once, on the first lookup that reads symbols (`live::ensure`, enabled by `main`; the tests leave it off), takes about 0.2 s and a 73 MB memory peak, and `malloc_trim` returns the memory on Linux. `docgen` documents the platform it runs on and the snapshot was made on Linux, so on macOS the live read lists a few hundred macOS-only symbols too: that is what a macOS user needs, and `test/live_test.c3` allows it (symbols both have must read identically). Locations are cut to `lib/std/...` wherever the server runs. docgen runs in the server's scratch directory (`proc::neutral_cwd`, `c3guide-<digits>` under the temp folder), and `env::PROJECT_PATH` evaluates to it: `live::entries_from_json` replaces that directory, and its real path when links make it differ (macOS `/private/var/...`), by `<project>`, as `gen_corpus.py` does for its own working directory. Symbols are one block sorted by name, in the snapshot (`gen_corpus.py` sorts) and in the live read, so an unchanged library ranks exactly like the snapshot. It is a port of `symbols()` in `scripts/gen_corpus.py`, and `test/live_test.c3` checks both give identical text for every symbol of the pinned compiler (run with `C3_DIR`). Change one, change the other. The `alias` variables (`mem`, `tmem`), the manual and the release notes always come from the snapshot. Any failure keeps the snapshot.
- `c3_lookup` (project part, and `path` alone), `c3_refs` and the 0.7 rewrite inside `c3_check` read source with the vendored tree-sitter C3 grammar (`vendor/`). `project_lookup` in `src/outline.c3` scans (`scan_files`, which `c3_refs` uses too, each file once) a project's `src`, the folders and files its `sources` name (`./*` is the project's own folder, read without what is below it; `dir/*` is shallow, `dir/**` deep) (when project.json names `sources`, only those: a folder it does not name is not read, with or without a `src/`; with none, `src`, else the whole project) and its `dependency-search-paths` (else `deps`), ranks each declaration by what it declares (`declared_name`: exact name, contains the name, mentions it) and shows the declarations that only mention a name in their parameters when nothing declares it. When nothing in the project declares the name (the best match only contains it) and the standard library has exactly it (one or two symbols), `c3_lookup` shows the library's answer first and the project's names after it. `refs_reply` walks the tree for identifier leaves, so comments and strings are not uses.
- A type lists its methods whatever module declares them (`tools::method_of`): a method belongs to a type by the type's name (`File` is in `std::io`, its `size` is declared in `std::io::file`); when two types share a name the modules must be the same or one inside the other. An alias (`alias Path = env::WIN32 ? PathWin : PathPosix;`) says what it stands for: the declaration is read from the installed library's source (`tools::alias_target`; found by name, the snapshot's row belongs to another release), the `env::WIN32` branch is chosen for the platform the server runs on, and the target's methods follow. Without the library's source the alias is shown as before.
- Ranking of `c3_search` (manual, recipes): BM25 as above, then an entry's score is multiplied by the square of the share of the typed words' weight (idf) it has (a section that repeats "type" does not beat one that has `sz` and "type"); a recipe gets the share to the power 0.8 instead, unless the query is a question about the language (8 or more words, or it opens with "what is"): the thread recipe of "start a thread and wait for it to finish" has few of the filler words and must stay. Both numbers were found against `search_tasks`, `paraphrase` and `quality` (found counts and MISS lists before and after are in the impl report), and among the best few a manual section that has a typed word in backticks (the manual's way to define a name) goes before one that does not (`search::prefer_defining_sections`). A question that opens with "what is", "what does", "explain", "difference between" is about the language: library names are added only when one is a word of the question (`search::asks_what_it_is`). A `$`, `$$` or `@` word of the query (punctuation around it is dropped: `($defined,`) is a name that must be in the text exactly: entries are ordered first by how many of those words they have (`Hit.marked`), then by score; and `tools::syntax_matches` puts the compiler's lists (keywords, builtins, attributes) that hold the word first. `$assignable` is gone since 0.8 (the manual snapshot still describes it): `recipes/compile_time.c3` shows `$defined(int v = x)`. The snapshot is 0.8.5, the install 0.8.6, so `scripts/update_recipes.py` refuses; the recipe records were refreshed with the same code from `gen_corpus.py` (`recipes()`) and the rest of the snapshot kept. `c3_lookup` of a name that does not exist adds `did you mean:` (at most 3, `src/suggest.c3`): the words of the missing name (a leading `t` is the temp variant, `get`/`new`/`is`/`to` are filler, `data/synonyms.txt` words count 0.7) against the words of the methods of the owner type, of the types that build it (`BUILDS`: String -> DString, ZString), the functions of the owner's module (the one named like it counts most) or of the module that was named; at least 0.6 of the words, and within 0.88 of the best score; a missing bare name is matched against type names (`Arena` -> `ArenaAllocator`); `libc::`/`posix::` names the library does not wrap get the extern hint instead. `test/suggest_test.c3` is the table of real misses. `c3_lookup Type.field` says it is a field and its type (`tools::field_reply`); `scope=syntax` with a name that is in no list points to the manual, the builtins list and `c3_lookup`.
- `c3_search scope=syntax` runs `c3c --list-<name>` of the installed compiler when its release is not the snapshot's (once per session), else it uses the snapshot lists. `scope=changes` with a version in the query (`0.8.5`, `v0.8.5`, `0.8.5_1`, `0.8`) returns that release's sections, newest first and the changes before the fixes (`tools::version_changes`); other words in the query filter their lines; a release the snapshot lacks says which ones it has. A question for the general search that merely holds a version (`c3_search` with scope all) falls back to the general release-notes search when the release has nothing about its words. `scope=changes` and the manual are always the snapshot; their replies say so when the compiler is another release (`manual_note`).
- The source and example parts of `c3_lookup` read the installed library (`compiler::stdlib_root`, the install directory or the one above it) and the recipes and manual examples.

## Updating for a new c3c release

Three pieces move at different speeds and are updated on their own:

| Piece | Where | Update |
|---|---|---|
| docs snapshot, synonyms | `data/` | `python3 scripts/gen_corpus.py /path/to/c3 [all.md]`, then `python3 scripts/update_synonyms.py` |
| C3 grammar | `vendor/tree-sitter-c3` | `python3 scripts/update_treesitter.py grammar [TAG]` |
| tree-sitter runtime | `vendor/tree-sitter` | `python3 scripts/update_treesitter.py runtime [TAG]` (rarely; the script checks the grammar's parser version still fits) |

`all.md` (`curl -o all.md https://c3-lang.org/all.md`) is optional and adds manual sections the install lacks. Also bump `C3C_VERSION` in `ci.yml` and `release.yml`; `sh test/version_check.sh` checks that both workflows pin the same c3c, that `project.json` has a version and that the server takes it from there.

The version is written in one place: `"version"` in `project.json`. c3c passes it to the code as `env::PROJECT_VERSION` (`VERSION` in `src/main.c3`), which `--version`, the usage text, `--doctor` and the MCP `serverInfo` report; `test/version_test.c3` checks they agree. Change it only with the maintainer's OK, and rebuild after changing it.

The grammar usually follows a c3c release by days or weeks, so a new snapshot never waits for it. To see whether the vendored grammar understands a compiler, run `C3_DIR=/path/to/c3 c3c test c3-guide-mcp`: one test parses every file of that c3c's standard library and fails, naming the files, if any does not parse. If it fails, ship the new snapshot with the old grammar (`git checkout vendor/`). Until the grammar catches up, the outline marks a file it could not fully read as incomplete and the rewrite in `c3_check` rewrites less, never more. CI runs the same test against the pinned c3c.

## Recipes

`recipes/*.c3` are small complete programs for the things models get wrong most. The first line is the title (it feeds search ranking, so keep it to what the program shows), `// expect:` lines are the exact output. `test/recipes_test.c3` compiles and runs each one. To add one: write the file, run `c3c test c3-guide-mcp`, then refresh the recipe records with `python3 scripts/update_recipes.py /path/to/c3` (it keeps every other record; `test/corpus_test.py` fails on stale recipes). `test/quality_test.c3` catches a title that pushes the wrong recipe down.

## Tests

```
C3_DIR=/path/to/c3 c3c test c3-guide-mcp   # tools, search quality, c3_check and its limits, recipes, grammar gate, live docs (about 80 s; needs sh, pgrep, pkill)
python3 test/stdio_test.py                 # JSON-RPC over the built binary
python3 test/smoke.py [binary]             # one call per tool (also run on Windows in CI)
python3 test/growth_test.py                # memory over 4,000 calls
python3 test/setup_test.py                 # --setup and --doctor on a throw-away HOME
python3 scripts/verify_corpus.py           # compile the code of the corpus; recipes must compile, manual blocks that do not are listed
python3 test/corpus_test.py /path/to/c3    # snapshot and synonyms match the c3c install
sh test/hook_test.sh                       # the Claude Code hook's matching rules
sh test/version_check.sh                   # version only in project.json, CI pins agree
```

The `@test` functions in `test/*.c3` call the tool functions directly, so no binary has to be built first. Without `C3_DIR` the grammar gate and the live-docs tests print "skipped" and pass; CI sets it. If your Claude Code uses the redirect hook, put `C3_GUIDE_ALLOW=1` in front of `c3c test`.

## Where the advice is written

The same advice appears in four places: each tool's `@Desc` (`src/tools.c3`, `src/check.c3`), `INSTRUCTIONS` in `src/main.c3`, `integrations/claude-code/CLAUDE.md` (also compiled into the binary for `--setup`), and the README. The `@Desc` is canonical: change it first, then bring the other three in line. `src/main.c3` also dispatches the command line modes handled by `src/setup.c3`.

## Corpus checks

`scripts/verify_corpus.py` compiles every recipe and every ```c3 block of the manual with the installed c3c. A recipe that fails is a bug (the script exits 1). A manual block that fails is either an illustration or a statement the compiler contradicts (an old keyword, a removed rule); read the list after a c3c release. A real contradiction goes into `ERRATA` in `scripts/gen_corpus.py` (applied when the corpus is generated; the script says when the manual was fixed and the entry can go).

## Safety design of the run tools

- On Linux and macOS, c3c and the programs it builds start in the scratch directory with a reduced environment (`KEEP_ENV` in `src/proc.c3`; on Windows the environment is inherited and the directory is ours): c3c reads every `*.c3l` in its working directory, so a snippet must not run in the directory the client started in, and API keys in the client's environment are not handed to a snippet's program.
- `c3_check` runs `c3c --trust=none --no-obj`: nothing is emitted or run. `$exec` does not run (tested with a positive control). `--trust=none` still allows `$embed`, which with `$echo` can print a file the server can read, so snippets containing `$embed`, `$include` or `$exec` are rejected before they reach the compiler. A project, file or `files` entry is read first by `src/guard.c3`. A project is read for **what c3c compiles**, not for its folder tree (`.work/`, `review/`, fixtures and a copy of the standard library in a project are never compiled, so they are not read): the files its `sources` and `test-sources` patterns stand for (the project's and every target's, `-override` keys too, as a union: a superset of any one call; the build never reads `test-sources`, the test command does, the union covers both), the libraries c3c can find (every `*.c3l` directly in each `dependency-search-paths` folder, else `.`, `lib` and `deps`: a library is found by what its manifest `provides`, not by its folder name, and may bring others, so every one is read, not only those `dependencies` names) with the sources their `manifest.json` names (union of all targets, plus the files of the library's own folder, which c3c takes when a target names none), and the sources inside `.c3l` archives. Patterns are expanded by `sources::expand_pattern`, the one definition shared with code + path (`project_files`); it follows c3c 0.8.6 (`target_expand_source_names` and `file_add_wildcard_files`, `src/utils/file_utils.c` in the compiler source; every rule below was probed with a sentinel file that exports a symbol, so a compiled file shows in `nm`): `dir/*` and `*` are the files of one folder, `dir/**` and `**` the folder and all below it (the folder part is used as written: `./`, `..`, `//`, an absolute path), a name ending in `.c3`, `.c3t` or `.c3i` (case matters) is a file, a name that is a folder (`src`, `src/`) is that folder with all below it, names that start with `.` are skipped in a walk (files and folders; a pattern may still name a hidden folder or file), links are followed (a file link needs a source name; a folder link is walked), a folder called `x.c3` is not entered, and only `.c3`, `.c3t` and `.c3i` names are sources. Everything else (`src/a*`, `src/**/`, `src/c?/x`) c3c refuses to build. **Fail closed**: when the project uses what the guard cannot expand exactly like c3c (a pattern c3c does not expand, `${NAME}` in a string, which c3c fills from the environment, a `template`, a project.json that is not plain JSON, more files than the limits below), the whole tree is read as it was before (nothing skipped, `.git` included, every folder `project.json` names as a tree of its own) and the answer begins with `(scanned the whole tree because ...)`. Never "accept". `$include` is refused by `--trust=none` before it reads anything (probed), so an included file need not be followed. The text of each file is read as c3c's lexer does: comments are skipped, but the contract lines of a doc comment (`<* @require ... *>`, from the first line that starts with `@name`) are code, and `<<*` / `int[<*>]` hold no doc comment (its own scanner, not `util::skip_blank`, which `hints` uses to copy comments). It refuses what it cannot prove, in one line (`src/x.c3:12: $embed path '/etc/passwd' leaves the project`, then the way out: c3_test, or build it yourself if you trust it): a compile-time read whose literal path ends outside the tree (absolute, `..`, a link), a computed or escaped or concatenated one (`"\x2e"`, `"a" +++ "b"`), any at all in a file that belongs to no project, a link in a compiled folder whose real path (every link of a chain resolved) is outside the tree or does not exist (a folder link is checked even when only data lies there now), a link named `x.c3l` to a directory that is not one (a library is told by its name), an unreadable or oversized source, a directory library (`*.c3l/`) whose `manifest.json` is missing, not JSON, or names a `sources` or `dependency-search-paths` folder outside the library, more than 5,000 files or 128 MB (a hostile repository is the case: `$embed` plus an `$assert` on one byte would read any file the server can read back, byte by byte). What c3c never reads is not checked: a link that leaves the project in a folder no pattern names, or a link to a non-source file in a source folder, is accepted. A link that ends inside the tree is not an escape: its target is read where it is compiled, a loop (a link to a folder being walked) is entered once, and relative `$embed` paths are checked from the link's folder and from the target's (c3c resolves them from the folder the file really lies in); on Windows `util::canonical` cannot resolve a link, so a link among the compiled files is refused there (not testable on Linux); the yaml-test-suite layout (1,500 links `name/x -> ../A2M4`) is a project that can be checked. `c3_test` and `c3_run` of a project directory are not guarded (they run the project's own code); the guard is for `c3_check` and for the project part of code + path. A project check is `-C` (type-check only): `cc` and the linker run the project's `cflags`, `c-sources` and `link-args`, which is code, so only `c3_test` and `c3_run` build.
- `src/compat.c3` sits in front of the library's handler (`compat::serve_stdio` is its stdio loop; `Server.handle` is called unchanged for everything else). It reads the arguments of a `tools/call`: `name` and `symbol` are `query` and `file` is `path` for a tool that takes that and has no `file` of its own (`c3_search` does); the real name wins when both are given, `name` before `symbol`; an argument the tool does not take is answered with the ones it takes (read from the tool's schema) and nothing runs; a call to a 0.5/0.6 tool (`c3_symbol`, `c3_examples`, `c3_outline`, `c3_syntax`, `c3_changes`, `c3_fix`) is forwarded to `c3_lookup` / `c3_search` / `c3_check` with a note in front of the answer. None of this is in the published schemas. A new tool needs no entry; a parameter renamed later needs one in `alias_of`.
- `code` together with `path` = a project directory (`c3_check`, `c3_run`): the snippet is written to the scratch directory and compiled with the project's files (`check::project_for_snippet`, `src/sources.c3`): the files the project-level `sources` stand for (the patterns as c3c expands them, see above; not a target's, not `test-sources`), `--libdir` for each `dependency-search-paths` entry (else `lib`, `deps`) and `--lib` for each of `dependencies`. The project is read by the guard first, as in path mode, and the snippet by the snippet guard (no `$embed`, `$include`, `$exec`). The project's `main` would clash with the snippet's, so when the snippet defines a `main` the source files that define one (`sources::defines_main`, `fn ... main(`) are left out of the command line, whole: a project that keeps other code in its main file loses it for that call. A snippet without `main` keeps every file (`c3_check` is a type-check, `--no-entry`). The project's `c-sources`, `cflags` and `link-args` are not used; at most 600 source files; nothing is written to the tree; paths in errors are the project's relative ones. `code` with a file as `path` is refused (`files` is for other sources).
- `c3_lookup` and `c3_refs` read a project's `dependency-search-paths` only when they stay inside the project or its parent folder (sibling libraries); other entries are skipped.
- Snippets and builds happen in a fresh temp directory (`c3guide-<nanoseconds>`), removed afterwards (the empty directory c3c runs in when it needs no files of its own is made once and removed when the server stops). A killed server leaves them behind; the next call removes `c3guide-<digits>` directories older than an hour (nothing else in the temp directory, symlinks are not followed).
- Every c3c run has a deadline (snippet 10 s, project check 25 s, `c3_test`/`c3_run` up to 120 s) and a capped output. A reader thread does the blocking read, so a call always returns. At the deadline c3c and everything under the scratch directory are killed (`pkill -f` on the escaped directory name; Linux and macOS).
- `c3_test`/`c3_run` execute what they build; the server is not a sandbox. The program's stdin is the `input` argument (16 KB), then end of input, so a program that reads stdin never waits for the deadline.
- The server finds `c3c` through `C3C`, `PATH`, then a few install locations (`find_c3c` in `src/compiler.c3`).

## CI and releases

`ci.yml` builds and smoke-tests on Linux, macOS and Windows and runs the full suite on Linux and macOS. `release.yml` builds the three archives and `SHA256SUMS` on a version tag. Windows compiles the vendored C with `clang` (`C3C_CC`).
